# ledger-morning-harness

タスク台帳（Google Sheets）を毎朝メンテナンスする、4エージェント直列のワークフロー（ハーネス）。

## 構成

4つの専任エージェントが、コードの構造で直列に並ぶ。前の段の完了後に必ず次が実行され、前段の結果（成否と要約）は次段へ渡される。時刻合わせや完了マーカーのポーリングは使わない。

| 段 | 役割 |
|---|---|
| 1. 新規収集（collect） | Issue・観測メモ・他システムの状態変化から、新しいタスクを拾って台帳へ登録する。登録前に、対象範囲の機械チェック（下記）をコード側で通す |
| 2. 現況更新・最新化（refresh） | 各行の対象（リンク先の Issue、関連ファイル等）を実際に見て、行を実態にそろえる |
| 3. 確認・前進（scan） | 前提の解消を確認し、次アクションを実行する。本人の判断が要る分だけを判断材料つきで上げる。あわせて Issue の停滞チェックも行う |
| 4. 報告（report） | 1〜3段の報告を整え、完了報告（報告なしの日も含む）を作る。送信は呼び出し側が行う |

各段の共通ルール：

- 失敗したら原因を特定して手段を変え、最大3回まで再試行する。段自体が失敗したら、ハーネスが失敗理由を引き継いでその段を再実行する（最大3回）
- 期日は自動で先に延ばさない
- 確認待ち・期日ありの待ちも毎朝実確認する（期日は確認を省く理由にならない）
- 行の削除はしない（完了行は残す）
- 報告は各段が構造化結果（status / summary / reports）として返し、呼び出し側が宛先ごとに届ける。ハーネス自体が落ちたら、呼び出し側が最大3回まで再起動する

## 対象範囲の機械チェック

台帳に載せるのは組織のタスクのみ、という原則を文章ではなくコードで担保する。

- 新規行：第1段は候補を集めるだけで書き込まず、ハーネスのコードが各候補の関連リンク（G列）を検証する。リンク先が対象組織の GitHub リポジトリ（組織リポジトリの Issue、または組織の実装リポジトリ）でない候補は登録せず、「対象外として弾いた行」として報告に必ず含める。通過した候補だけを登録係が書き込む
- 既存行：毎朝、全行について同じ検証を行い、組織リンクの無い行は「範囲漏れの疑い」として報告に必ず含める（自動削除はしない）

## 動かし方

Muse のワークフローとして保存し、毎朝の cron から引数 `{ "date": "YYYY-MM-DD" }` で起動する。

## 置換が必要な箇所

公開用に実値を伏せてある。使う環境に合わせて置き換えること。

- `__SPREADSHEET_ID__` — 対象スプレッドシートの ID
- `__ORG_REPO__` — 停滞チェック対象の Issue リポジトリ（owner/name）
- `__ORG_OWNER__` — 対象範囲チェックで使う、組織リポジトリの所有者名
- `__ORG_REPO_NAME__` — 対象範囲チェックで使う、組織リポジトリの名前（`__ORG_REPO__` の name 部分）
